# النشر على Vercel — دليل تنفيذي

هذا المستند وصفة كاملة من الصفر إلى موقع يعمل، مع الأرقام الرسمية التي **تحقّقنا منها**.
الحدود تقرأ من مستندات المزوّدين بتاريخ **2026-10-21**؛ أعِد التحقق قبل الاعتماد لأنها تتغيّر.

> **ما لم يُنفَّذ:** النشر الفعلي على Vercel. لا يوجد حساب Vercel ولا توكن Blob في بيئة البناء،
> لذلك كل ما يخصّ المنصة هنا موثّق من المستندات الرسمية + الكود، لا من تجربة حيّة.
> راجع §14 قبل اعتبار أي بند مضمونًا.

---

## 0) ما تحتاجه

- مستودع GitHub يحوي المشروع **في الجذر** (لا مجلد `project/` داخلي).
- حساب على Vercel.
- قاعدة Postgres مُدارة (المثال هنا Neon، وأي مزوّد يعمل).
- نطاق خاص (اختياري لكنه مطلوب للثقة ولـ`NEXT_PUBLIC_SITE_URL` النهائي).

---

## 1) أنشئ قاعدة البيانات (Neon مثالًا)

1. أنشئ مشروعًا جديدًا واختر منطقة قريبة من جمهورك (مثل `eu-central-1`).
2. من صفحة الاتصال اختر **Pooled connection** — وليس الاتصال المباشر — لأن دوال Vercel قصيرة العمر
   وتفتح اتصالات كثيرة. التطبيق يضبط `prepare: false` و`max: 3` أصلًا (`db/index.ts`).
3. انسخ الرابط وأضف `?sslmode=require` إن لم يكن موجودًا.

**الخطة المجانية من Neon (مُتحقَّق منها في `neon.com/pricing`):** مشروع بسعة **1 GB**،
و**100 CU-hours** شهريًا لكل مشروع، وأحجام حتى 2 CU. القاعدة تتوقف عند الخمول وتستأنف تلقائيًا،
وهذا مناسب لموقع منخفض الحركة. البدائل: Supabase، أو Postgres على VPS.

> لا تكتب رابط القاعدة في المستودع ولا في أي ملف يُرفع. ضعه في متغيّرات البيئة فقط.

---

## 2) جهّز القاعدة قبل أول نشر (من جهازك)

```bash
npm ci
export DATABASE_URL="postgresql://USER:PASSWORD@HOST/DB?sslmode=require"

npm run db:migrate                                   # ينشئ كل الجداول من db/migrations
npm run admin:password -- admin@your-domain.com "كلمة-مرور-قوية"
npm run check:data                                   # فحص سلامة البيانات
```

- **لا تشغّل `npm run db:seed` على قاعدة شبكية.** السكربت يرفض ذلك إلا بـ`SEED_DEMO=1`،
  والبيانات تجريبية. للإطلاق الحقيقي: أنشئ المحتوى من اللوحة أو استورده.
- لبيئة تجريبية (staging) فقط، إن أردت بيانات العرض:
  `SEED_DEMO=1 npm run db:seed`.
- **قبل الإطلاق، نظّف المحتوى التجريبي بأمر واحد:**
  `npm run demo:flush -- --yes --people` (يحذف الأعمال الموسومة `is_demo` وملحقاتها والأشخاص
  التجريبيين بلا أرصدة، ويُطفئ لافتة «محتوى تجريبي»، ويسجّل العملية في التدقيق). ثم `npm run check:data`.
  تحقّقنا منه محليًا: القاعدة أصبحت 0 عمل و0 شخص، وكل صفحات المتجر بقيت 200 بحالات فارغة.
- `admin:password` يُنشئ الحساب إن لم يكن موجودًا ويُبطل جلساته القديمة، ولا يطبع كلمة المرور.

## 3) استورد المستودع إلى Vercel

1. **Add New → Project → Import Git Repository** واختر المستودع.
2. اترك **Root Directory** فارغًا/`./` — المشروع في جذر المستودع.
3. Framework Preset: **Next.js** (يُكتشف تلقائيًا). Build: `next build`. Install: `npm ci`.
4. Node.js 20 أو أحدث.

**هل يحتاج البناء إلى قاعدة بيانات؟** لا في الوضع الحالي: كل صفحات الموقع تقريبًا
`force-dynamic` ولا تُولَّد في البناء (تحقّقنا: سجلّ التوليد يحتوي 3 مسارات ثابتة فقط،
منها `robots.txt`). ومع ذلك اترك `DATABASE_URL` متاحًا في بيئة البناء احتياطًا لأي مسار ثابت يُضاف لاحقًا.

## 4) متغيّرات البيئة (Production وPreview)

| المتغيّر | إلزامي | القيمة | ملاحظات |
|---|---|---|---|
| `DATABASE_URL` | ✅ | رابط Postgres المجمّع + `sslmode=require` | سرّي |
| `NEXT_PUBLIC_SITE_URL` | ✅ | `https://your-domain.com` بلا `/` في النهاية | يدخل في canonical وOG وsitemap |
| `APP_SECRET` | ✅ | 32 حرفًا عشوائيًا (`openssl rand -base64 32`) | سرّي |
| `SESSION_COOKIE_NAME` | اختياري | `loomix_session` | غيّره لعزل بيئتين على النطاق نفسه |
| `UPLOAD_MAX_MB` | اختياري | `4` في الإنتاج | سقف جسم الطلب عند Vercel 4.5MB (انظر §7) |
| `BLOB_READ_WRITE_TOKEN` | اختياري | يُحقن تلقائيًا عند ربط مخزن Blob | سرّي، لا تكتبه يدويًا |
| `TMDB_API_KEY` | اختياري | مفتاحك | يبقى معطّلًا حتى تفعّل مزامنة المصادر وتراجع شروطها |

**لا تضبط هذه في الإنتاج إطلاقًا:**

- `SHOW_DEMO_CREDENTIALS` — يعرض بيانات الدخول لأي زائر.
- `SEED_DEMO` — يسمح بمحو القاعدة وزرع بيانات تجريبية.

`ADMIN_EMAIL`/`ADMIN_PASSWORD`/`ADMIN_NAME` تُستخدم فقط عند `db:seed`، ولسنا نستخدمه في الإنتاج،
فلا حاجة لوضعها على Vercel.

## 5) أول نشر، ثم فحص

بعد انتهاء أول Deploy:

```bash
npm run smoke -- https://your-project.vercel.app --prod
npm run smoke -- https://your-project.vercel.app --crawl
curl -s https://your-project.vercel.app/api/health
```

- `--prod` يمنع ظهور أي بيانات دخول تجريبية.
- المتوقّع: **0 خطأ**. التحذير الوحيد المسموح محليًا هو HSTS على http؛ على https يجب ألا يظهر.
- `/api/health` يجب أن يعيد `200` و`{"status":"ok","db":"up"}`، و`503` إن تعطّلت القاعدة.
  هذا المسار لا يكشف أسرارًا ولا نص خطأ، ويُرسل `Cache-Control: no-store` و`X-Robots-Tag: noindex`.

جرّب بعدها المسار الكامل: دخول المدير → إنشاء عمل → نشره → ظهوره في `/latest` و`sitemap.xml`.

---

## 6) النطاق

1. **Settings → Domains → Add**، ثم أضف سجلات DNS التي تطلبها المنصة.
2. انتظر إصدار الشهادة (HTTPS تلقائي).
3. **حدّث `NEXT_PUBLIC_SITE_URL` إلى النطاق النهائي ثم أعد النشر.** بدونه ستشير canonical
   وOG وsitemap إلى نطاق Vercel المؤقت.
4. تحقّق: `curl -sI https://your-domain.com | grep -i strict-transport` (HSTS موجود في الإنتاج)،
   وأن `sitemap.xml` يحوي نطاقك.

## 7) الصور والرفع — **إلزامي قبل استخدام اللوحة في الإنتاج**

**المشكلة:** `public/uploads` نظام ملفات مؤقت على Vercel؛ أي صورة تُرفع من اللوحة تختفي
بعد النشر التالي أو إعادة تشغيل الدالة.

**المدعوم الآن في الكود:** `lib/storage.ts` يختار التخزين تلقائيًا:

| الحالة | أين تُكتب الصور | المسار المخزَّن في القاعدة |
|---|---|---|
| بلا `BLOB_READ_WRITE_TOKEN` (محلي) | `public/uploads` | `/uploads/<id>-<w>.webp` |
| مع توكن Vercel Blob | مخزن Blob | `https://<store>.public.blob.vercel-storage.com/uploads/…` |

**الخطوات على Vercel:**

1. **Storage → Blob → Create Store** ثم اربطه بالمشروع. يُحقن `BLOB_READ_WRITE_TOKEN` تلقائيًا.
2. أعد النشر. لا حاجة لأي تعديل في الكود.
3. `next.config.ts` يسمح أصلًا بنطاق `*.public.blob.vercel-storage.com` في `images.remotePatterns`
   وفي `img-src` بسياسة CSP — بدون ذلك يفشل `next/image` أو يحجب المتصفح الصورة.

**حدود Blob على Hobby (مُتحقَّق منها):** تخزين **1 GB**، **10,000** عملية بسيطة،
**2,000** عملية متقدمة، **10 GB** نقل بيانات شهريًا. عند تجاوز أي حد يتوقف الوصول للمخزن
حتى 30 يومًا — راقب الحجم قبل رفع أرشيف كبير.

**سقف حجم الطلب:** Vercel يرفض أي جسم طلب يتجاوز **4.5 MB** بحالة `413` قبل وصوله للتطبيق.
لذلك اضبط `UPLOAD_MAX_MB=4` ليعطي رسالة عربية واضحة بدل خطأ المنصة. (محليًا الافتراضي 6MB.)

**مزوّد آخر (S3/R2/MinIO):** عدّل `putImage` في `lib/storage.ts` لرفع موقّع (SigV4)، وأبقِ
شكل المخرَج كما هو (رابط `https` كامل أو `/uploads/...`)، ثم أضف نطاق التخزين إلى
`images.remotePatterns` و`img-src` في `next.config.ts`. هذه الطريقة **غير مُنفَّذة ولا مُختبرة** هنا.

**صور العرض التجريبي** في `public/art/` مرفوعة مع المستودع (2.4MB) وتعمل دون أي تخزين خارجي.

> **ملاحظة مُتحقَّق منها محليًا:** في وضع `next start` يفحص Next مجلد `public/` عند الإقلاع،
> فالصورة المرفوعة بعد الإقلاع تُكتب على القرص لكنها تعيد **404** حتى إعادة تشغيل الخادم.
> هذا لا يظهر في `next dev` ولا يؤثر عند استخدام Blob (الرابط يُخدم من المخزن فورًا)،
> وهو سبب إضافي لعدم الاعتماد على القرص في الإنتاج.

## 8) الكاش وإعادة التحقق

- صفحات الموقع `force-dynamic` وقراءاتها مُخزَّنة بـ`unstable_cache` تحت وسم `catalog`.
- كل إجراء في اللوحة يستدعي `revalidateTag` فورًا، فلا حاجة إلى إعادة بناء أو Cron لإظهار التعديلات.
- على Hobby: **Cron بحد أدنى مرة كل يوم** (التعبيرات الأكثر تكرارًا تفشل أثناء النشر)،
  و100 مهمة كحد أقصى للمشروع. لا تستخدمه إلا لمزامنة مصدر خارجي بطيء.

## 9) النسخ الاحتياطي والاستعادة

| الطريقة | تعمل على Vercel؟ | ملاحظة |
|---|---|---|
| زر «تنزيل JSON» في `/admin/backup` | ✅ | يمرّ عبر المتصفح، لا يعتمد على القرص |
| «إنشاء نسخة على الخادم» | ❌ | يكتب في `backups/` وهو مؤقت |
| `pg_dump` من جهازك | ✅ | الطريقة الموصى بها |

```bash
pg_dump "$DATABASE_URL" --no-owner --format=custom -f "loomix-$(date +%F).dump"

# استعادة
pg_restore --clean --no-owner -d "$DATABASE_URL" loomix-YYYY-MM-DD.dump
npm run check:data
```

- الصور ليست داخل القاعدة: احتفظ بنسخة من مخزن Blob (أو من `public/uploads` محليًا).
- خذ نسخة قبل أي هجرة كاسرة؛ الهجرات إلى الأمام فقط.

## 10) المراقبة والسجلات

- **Uptime:** أضف مراقبًا خارجيًا (UptimeRobot / BetterStack / غيره) على
  `https://your-domain.com/api/health` كل 5 دقائق، مع تنبيه عند `503` أو انقطاع.
- **السجلات:** على Hobby تُحفظ Runtime Logs **ساعة واحدة** فقط. لا تعتمد عليها للأرشيف؛
  استخدم مراقبًا خارجيًا، أو Pro (يوم كامل) أو Drain.
- **الأخطاء:** التطبيق لا يعرض تفاصيل داخلية للمستخدم؛ تفاصيل الخطأ تُكتب في سجلّ الخادم فقط.

## 11) حدود Vercel Hobby المؤكدة (2026-10-21)

المصادر: <https://vercel.com/docs/limits> · <https://vercel.com/docs/functions/limitations> ·
<https://vercel.com/docs/plans/hobby> · <https://vercel.com/docs/cron-jobs/usage-and-pricing> ·
<https://vercel.com/docs/vercel-blob/usage-and-pricing> · <https://vercel.com/pricing>

| المورد | حد Hobby | ما يعنيه لـLoomix |
|---|---|---|
| زمن تنفيذ الدالة | **300 ثانية** كحد أقصى | رفع الصور `maxDuration=30`؛ الاستيراد بدفعات 10 صفوف |
| جسم الطلب/الاستجابة | **4.5 MB** (413 عند التجاوز) | `UPLOAD_MAX_MB=4`، واستيراد CSV/JSON محدود بـ2MB |
| حجم حزمة الدالة | 250 MB غير مضغوط | مساحة مريحة؛ `sharp` و`postgres` خارج الحزمة |
| الاستدعاءات | **1,000,000/شهر** | كل صفحة ديناميكية = استدعاء؛ ~33 ألف/يوم |
| Active CPU | **4 ساعات/شهر** | كافية لموقع منخفض الحركة |
| Provisioned Memory | 360 GB-ساعة/شهر | — |
| Fast Data Transfer | **100 GB/شهر** | صور/صفحات |
| Fast Origin Transfer | **10 GB/شهر** | — |
| CDN Requests | 1,000,000/شهر | — |
| تحويلات الصور | **5,000/شهر** (قراءات كاش 300k، كتابات 100k) | إن تجاوزتها استخدم `unoptimized` أو صورًا بأحجام مسبقة |
| عمليات النشر | 100/يوم، **بناء متزامن واحد**، 45 دقيقة للبناء | لا تدفع دفعات صغيرة متلاحقة |
| Cron | 100 مهمة · **أدنى فاصل: مرة يوميًا** | لا تعتمد عليه للتحديث الفوري |
| سجلات التشغيل | **ساعة واحدة** | مراقب خارجي |

**ملاحظة مهمة:** لأن كل صفحات الموقع تقريبًا ديناميكية، كل زيارة تستهلك استدعاء دالة.
إن اقتربت من مليون شهريًا فالخطوة التالية ليست ترقية فورية بل تحويل الصفحات الأكثر زيارة
إلى ISR/كاش CDN (تغيير في الكود) — أو ترقية الخطة.

## 12) قيد الاستخدام التجاري ومتى ترقّي

مستندات Vercel تنصّ صراحةً أن خطة **Hobby مخصّصة للاستخدام الشخصي غير التجاري**
(<https://vercel.com/docs/plans/hobby> → fair use guidelines). إن كان Loomix موقعًا عامًا
يجلب دخلًا (إعلانات/اشتراكات/رعاية) فالخطة الصحيحة هي **Pro: 20$/شهر** مع رصيد استخدام 20$
(<https://vercel.com/pricing>، مُتحقَّق منه في 2026-10-21).

**مؤشرات الترقية:**

| المؤشر | الإجراء |
|---|---|
| استخدام تجاري أو علامة تجارية | Pro إلزامي |
| تجاوز 1M استدعاء أو 100GB نقل | Pro (أو كاش/ISR أولًا) |
| أكثر من 1GB صور | Pro / نقل إلى R2 |
| الحاجة إلى Cron كل ساعة أو أدق | Pro |
| الحاجة إلى سجلات > ساعة أو بناء متزامن | Pro |
| استيراد جماعي كبير متكرر | Pro (زمن أطول) أو عامل خارجي |

وثّق قرار الترقية وتاريخه في ملف التشغيل الخاص بك.

## 13) التراجع وخطة الخروج

- **تراجع عن نشر:** Deployments → اختر النشر السابق → **Instant Rollback**. لا يمسّ قاعدة البيانات.
- **تراجع عن هجرة:** استعادة من `pg_dump` (الهجرات لا تُعكس تلقائيًا).
- **الخروج من Vercel:** المشروع Next.js عادي؛ أي منصة Node 20+ (Render/Railway/VPS + Nginx)
  تشغّله بأمر `npm run build && npm start` مع المتغيّرات نفسها.
- **الخروج من Neon:** `pg_dump` ويُستعاد على أي Postgres 15+.
- **الخروج من Blob:** نزّل الملفات (أو انسخها بـrclone) وحدّث `media_assets.path` وحقول
  البوستر/الخلفية مرة واحدة، وأضف النطاق الجديد إلى `remotePatterns` و`img-src`.

---

## 14) ما لم يُختبر (ولا يُقدَّم كضمان)

1. **النشر الفعلي** على Vercel — لم يُنفَّذ من بيئة البناء.
2. **Vercel Blob** — مسار التخزين السحابي مكتوب ومربوط بالتوكن، لكن لم يُجرَّب رفع حقيقي
   (لا يوجد توكن). المسار المحلي مُختبَر (رفع 415/401/نجاح في `npm run e2e`).
3. **الحدود تحت حمل حقيقي** — الأرقام من المستندات، لا من قياس.
4. **الشهادات والنطاق** — تعتمد على DNS لديك.
5. **Neon** — لم يُنشأ مشروع فعلي؛ الأرقام من صفحة الأسعار.

عند تنفيذ النشر لأول مرة، سجّل نتيجة كل بند هنا وأزل وسم «غير مُختبر».
