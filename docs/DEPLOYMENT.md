# النشر والتشغيل — Loomix

هذا المستند يشرح كيف يعمل Loomix خارج جهازك، وما القيود التي **تحقّقنا منها** وما لم نتحقق منه بعد.
القاعدة: لا نعتمد على رقم أو حصة مجانية لم نراجعها في المصدر الرسمي وقت التنفيذ.

---

## 1) ما يحتاجه التطبيق فعلًا

| المكوّن | محليًا | في الإنتاج |
|---|---|---|
| Next.js 16.4.2 (App Router · Turbopack) | `next dev` | منصة تدعم Node ≥ 20.9 (مثل Vercel) |
| قاعدة بيانات Postgres | PGlite داخل `.data/pglite` | Postgres مُدار (Neon / Supabase / غيرها) |
| الملفات المرفوعة | `public/uploads` | Vercel Blob (جاهز بلا تعديل كود) أو S3/R2 — **إلزامي** |
| التريلرات | تضمين YouTube | تضمين YouTube فقط |

PGlite **للتطوير فقط**: ملفاتها على القرص المحلي، وسلوكها مع دوال Serverless غير مناسب.

---

## 2) متغيّرات البيئة على المنصة

انسخ من `.env.example` وأضف في إعدادات المنصة:

- `DATABASE_URL` — رابط Postgres مع `sslmode=require`. استخدم Pooler إن توفّر.
- `NEXT_PUBLIC_SITE_URL` — النطاق النهائي (بدون `/`).
- `CRON_SECRET` — سرّ مهمة الصيانة اليومية (`/api/cron/maintenance`). بلا ضبطه تبقى المهمة معطّلة.
- `SESSION_COOKIE_NAME` — افتراضيًا `loomix_session`.
- `APP_SECRET` — 32 حرفًا عشوائيًا على الأقل.
- `ADMIN_EMAIL` / `ADMIN_PASSWORD` / `ADMIN_NAME` — تُستخدم مرة واحدة عند التهيئة.

> لا تضع أي مفتاح سري في متغيّر يبدأ بـ `NEXT_PUBLIC_`. كل هذه المفاتيح تُقرأ على الخادم فقط.
> `.env` مستثنى في `.gitignore`، ويُرفع `.env.example` وحده.

## 3) أول نشر (خطوة بخطوة)

```bash
# 1) محليًا: رقم الهجرات ثم البيانات التجريبية (اختياري للإنتاج)
npm ci
npm run db:migrate

# 2) في الإنتاج: طبّق الهجرات على قاعدة البيانات المُدارة
DATABASE_URL="postgresql://…" npm run db:migrate

# 3) أنشئ حساب المدير (بدون بيانات تجريبية — db:seed محظور على قاعدة شبكية)
DATABASE_URL="postgresql://…" npm run admin:password -- admin@example.com "كلمة-قوية"

بعد الاستعادة أو أي تغيير في البيانات، شغّل فحص السلامة:
`DATABASE_URL="postgresql://…" npm run check:data` — يخرج بكود غير صفري عند أي خلل.

**لا تُفعّل `SHOW_DEMO_CREDENTIALS` في الإنتاج.** المفتاح الافتراضي غير موجود، وبغيابه
لا تُطبع أي بيانات دخول في صفحة `/login`. فعّله محليًا فقط إن أردت تذكيرًا أثناء التطوير.

# 4) ابنِ وتحقّق
npm run typecheck
npm run build

# 5) الفحص النهائي قبل النشر (يقرأ البيئة ويتصل بالقاعدة)
DATABASE_URL="postgresql://…" NEXT_PUBLIC_SITE_URL="https://your-domain.com" \
  SHOW_DEMO_CREDENTIALS=0 npm run preflight -- --prod
```

`preflight` يفشل (كود 1) عند: سر تشغيلي ضعيف أو مثال، PGlite في الإنتاج، رابط موقع يشير إلى
localhost، تفعيل بيانات الدخول التجريبية، بقاء كلمة مرور افتراضية لأي حساب إداري، غياب حساب
مدير، غياب لافتة المحتوى التجريبي مع وجود محتوى موسوم، أو وجود حدث في سجل العمليات بلا تسمية
عربية في `app/(admin)/admin/audit/page.tsx` (فحص ثابت يقرأ الكود ولا يحتاج قاعدة بيانات). ويحذّر عند تخزين الصور على قرص
محلي في بيئة بلا تخزين دائم.

`db:seed` يحرس نفسه: يرفض العمل على قاعدة شبكية أو في بيئة إنتاج إلا مع `SEED_DEMO=1`،
لأنه يبدأ بمسح كل الجداول.

بعد النشر — **فحص دخان من خارج المنصة** (HTTP فقط، بلا وصول لقاعدة البيانات، آمن على الإنتاج):

```bash
npm run smoke -- https://your-domain.com --prod --crawl
```

يتحقّق من: 200 للرئيسية، `lang="ar" dir="rtl"`، CSP وX-Frame-Options وReferrer-Policy
وX-Content-Type-Options وغياب X-Powered-By وHSTS على https، محتوى `robots.txt`، عدد روابط
`sitemap.xml` وأنها من نفس النطاق، 404 حقيقي لمسار غير موجود، حماية `/admin` بالتوجيه إلى
`/login`، خلوّ صفحة الدخول من كلمات المرور التجريبية (مع `--prod`)، صلاحية JSON-LD ووجود
`Organization` + `WebSite`، كاش الأصول `immutable`، وعمل `/api/search`. مع `--crawl` يفتح
أول 40 رابطًا من الخريطة.

كود الخروج 1 يعني: **لا تُعلن الرابط بعد** — عالج الأخطاء أولًا. شغّله أيضًا بعد كل نشر لاحق
كفحص تراجع سريع.

### فحص شامل للوحة (بيئات الاختبار فقط)

```bash
npm run e2e -- --base http://localhost:3000
```

يسجّل الدخول كمدير ويمرّ على المسار الكامل بلا متصفح: إنشاء عمل (POST أصلي بلا JS) ← مسودة
تعيد 404 ← نشر من صف القائمة ← ظهوره للجمهور ← تعديل حقل ← صفحة تأكيد الحذف ← الحذف ← اختفاؤه
من الواجهة واللوحة والخريطة. ثم يفحص طرد المشاهد من `/admin`، ورفض ملف متنكّر كصورة (415)
ورفض الرفع بلا جلسة (401)، وإبطال الجلسة عند الخروج. 16 فحصًا، وكلها تُنظّف جلستها في النهاية.

**لا تشغّله على الإنتاج**: ينشئ بيانات ويحذفها، ويضيف صفوفًا إلى سجل التدقيق وحدود المعدل.
شغّله على بيئة معاينة أو محليًا؛ `--keep` يُبقي العمل التجريبي للمعاينة اليدوية.

على Vercel: اربط المستودع، أضف المتغيّرات، واضبط أمر البناء `npm run build`.
البيانات التجريبية (24 عملًا) ليست للنشر العلني؛ استخدم `npm run db:reset` للمسح وإعادة التهيئة محليًا،
وبدون تشغيل `db:seed` في الإنتاج تبدأ بقاعدة فارغة تمامًا.

## 3.1) إن فشل PGlite المحلي بـ `Aborted()`

PGlite يعمل داخل العملية على مجلد `.data/pglite`، وإيقاف الخادم إيقافًا قسريًا أثناء الكتابة
يترك `postmaster.pid` قديمًا فيرفض التشغيل التالي الفتح. هذا خلل بيئة تطوير فقط (الإنتاج يستخدم
Postgres مُدارًا)، وعلاجه:

```bash
# 1) تأكّد ألّا خادمًا يعمل
ss -ltnp | grep 3000
# 2) أعد بناء قاعدة العرض (بيانات تجريبية فقط — لا تفعلها على قاعدة فيها محتوى حقيقي)
rm -rf .data/pglite && npx tsx db/migrate.ts && npx tsx db/seed.ts
```

**لا تفتح PGlite من سكربت بينما الخادم يعمل**: القفل أحادي العملية، فأي `check:data` أو سكربت
`node` متزامن قد يفسد الملفات. أوقف الخادم أولًا، أو استخدم Postgres محليًا إن احتجت وصولًا متوازيًا.

**انتظر خروج العملية فعلًا قبل فتح السكربت.** `kill` ثم `sleep 2` لا يكفيان دائمًا: إذا بقي المنفذ
مفتوحًا أو بقيت العملية فإن السكربت التالي يتصارع معها على القفل ويُفسد الملفات (حدث فعليًا أثناء
الاختبار، فاحتجنّا لإعادة البناء). تحقّق أن `ss -ltnp | grep 3000` لا يعيد شيئًا، ثم انتظر ثانيتين
إضافيتين، أو استخدم `kill -9` للعملية المعلّقة.

**حذف `postmaster.pid` وحده لا يكفي.** جُرّب في 2026-10-21: بعد إيقاف `next start` أثناء كتابة، صار
كل فتح لـ`PGlite` ينتهي بـ`RuntimeError: Aborted()`، وحذف `.data/pglite/postmaster.pid` لم يُصلح
شيئًا لأن WAL تُرك بحالة غير مكتملة. الحل الوحيد الموثوق هو إعادة البناء (الأمر أعلاه)، وهو آمن
هنا لأن كل المحتوى بيانات عرض مولّدة من `db/seed.ts`.

## 4) قيود Vercel التي يجب التعامل معها

> **حُدِّثت في 2026-10-21**: راجعنا المستندات الرسمية وسجّلنا الأرقام المؤكدة في
> [`docs/DEPLOY-VERCEL.md`](./DEPLOY-VERCEL.md) (§11). هذا القسم يبقى ملخّصًا عمليًا،
> والدليل التنفيذي الكامل (خطوة بخطوة) هناك.

الروابط الرسمية:

- <https://vercel.com/docs/limits>
- <https://vercel.com/docs/functions/limitations>
- <https://vercel.com/docs/plans/hobby>
- <https://vercel.com/pricing>

1. **نظام ملفات مؤقت.** لا تكتب في `public/uploads` أو `backups/` في الإنتاج.
   - الرفع: `app/api/admin/upload/route.ts` يكتب محليًا الآن. للاستبدال: ارفع إلى S3/R2 وأعد المسار.
   - النسخ الاحتياطي: زر «تنزيل JSON» يعمل دائمًا؛ «إنشاء نسخة على الخادم» مخصّص للبيئات ذات قرص دائم.
2. **مدة تنفيذ الدوال محدودة.** لذلك:
   - الاستيراد الجماعي يعمل **على دفعات 10 صفوف**، والحالة محفوظة في `import_jobs`.
   - فحص التريلرات له مهلة 6 ثوانٍ لكل رابط، لا فحص جماعي في طلب واحد.
3. **لا عمليات خلفية دائمة.** كل ما يحتاج وقتًا طويلًا يُشغَّل من المتصفح بدفعات، أو من Cron خارجي.
4. **إعادة التحقق.** التحديثات في اللوحة تستخدم `revalidateTag("catalog" | "homepage")` فورًا.
   لا حاجة إلى Cron لإعادة البناء. إن أضفت مصدرًا خارجيًا يتغيّر يوميًا، استخدم Cron يوميًا يضرب مسارًا محميًا.
5. **حدود الطلبات وحجم الجسم.** رفع الصور محدود بـ 6MB، والاستيراد بـ 2MB. تحقّق من حدود المنصة قبل رفعها.

## 5) قاعدة البيانات

- المخطط في `db/schema.ts`، والهجرات في `db/migrations/`.
- الصور تُحفظ كمسارات نصية (`/uploads/...` أو رابط خارجي).
- الحذف: `titles` يحذف المواسم والحلقات والتريلرات والارتباطات عبر `on delete cascade`؛ سجل العمليات يبقى.
- Indexes أساسية: `titles(type,state)`, `titles(slug)`, `(title_ar, release_year) unique`, `seasons(title_id, number) unique`,
  `episodes(season_id, number) unique`, `title_views(title_id, created_at)`.

**الهجرة على Postgres:** `npm run db:migrate` يقرأ `DATABASE_URL` وينفّذ ملفات `db/migrations` بالترتيب.

## 6) تخزين الصور

`sharp` ينتج ثلاثة أحجام WebP (400/900/1600)، ثم `lib/storage.ts` يختار وجهة التخزين:

| الحالة | الوجهة | ما يُخزَّن في القاعدة |
|---|---|---|
| بلا `BLOB_READ_WRITE_TOKEN` | `public/uploads` (تطوير محلي) | `/uploads/<id>-<w>.webp` |
| مع توكن Vercel Blob | مخزن Blob (إنتاج) | رابط `https://…` كامل |

- **Vercel:** اربط مخزن Blob بالمشروع فقط — لا تعديل في الكود. التفاصيل في `DEPLOY-VERCEL.md` §7.
- **S3/R2:** عدّل `putImage` في `lib/storage.ts` لرفع موقّع، وأضف نطاق التخزين إلى
  `images.remotePatterns` و`img-src` في `next.config.ts`. **غير مُنفَّذ ولا مُختبر هنا.**
- انقل الملفات القديمة مرة واحدة، وحدّث `media_assets.path` وحقول البوستر/الخلفية إن تغيّر النطاق.
- سقف الصورة: `UPLOAD_MAX_MB` — افتراضي **6 محليًا و4 على Vercel تلقائيًا** (سقف جسم الطلب هناك 4.5MB)، وأي قيمة أعلى تُقيَّد بـ4 هناك ليعطي النظام رسالته العربية بدل خطأ المنصة.

الخروج من خدمة التخزين: كل المسارات نصوص عادية؛ نقلها إلى نطاق آخر = تحديث عمود واحد + إعادة رفع الملفات.

## 7) الاعتماد على YouTube

المشغّل يستخدم `youtube-nocookie.com` عبر iframe، ولا يُحمّل أي سكربت من يوتيوب قبل نقر المستخدم.
إن فشل التضمين: الواجهة تُظهر رابط «فتح على يوتيوب» بدل إطار فارغ.
فحص الحالة يستخدم `oEmbed` الرسمي؛ عند فشل الشبكة **لا نخمّن**: تبقى الحالة «لم يُفحص».

## 8) خطة الخروج لكل خدمة

| الخدمة | ما يعتمد عليها المشروع | البديل | التكلفة |
|---|---|---|---|
| Vercel | استضافة Next | أي منصة Node (Render / Railway / VPS + Nginx) | تغيير إعدادات النشر فقط |
| Postgres مُدار | البيانات | أي Postgres 15+ (Supabase، RDS، VPS) | تصدير SQL قياسي |
| تخزين الكائنات | الصور | S3/R2/MinIO | مسارات نصية، نقل ملفات |
| YouTube | التريلرات | Vimeo أو ملفات رسمية مسموح تضمينها | تعديل عمود `youtube_id` + المشغّل |

لا يوجد أي تبعية لخدمة مغلقة لا يمكن تصدير البيانات منها: النسخ الاحتياطي JSON + هجرات SQL قياسية.

---

## 9) ما لم يُختبر بعد

- النشر الفعلي على Vercel (لا يوجد حساب في بيئة البناء).
- **حدود الحصص**: راجعنا مستندات Vercel وNeon الرسمية في 2026-10-21 وسجّلناها في
  `DEPLOY-VERCEL.md` §11 — لكن **لم نقسها تحت حمل حقيقي**.
- **Vercel Blob**: مسار التخزين مكتوب ومربوط، ولم يُجرَّب رفع حقيقي (لا توكن).
- تحمّل الضغط العالي وتجمّع الاتصالات على Pooler.
- فحص التريلرات على شبكة إنتاج (الشبكة محجوبة جزئيًا في بيئة البناء).

هذه النقاط موثّقة كـ«غير مُتحقَّق» ولا تُقدَّم كضمانات.
